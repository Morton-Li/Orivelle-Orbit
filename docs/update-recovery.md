# 更新恢复的当前实现

本阶段提供 macOS 更新事务的项目内实现和故障夹具。正式渠道、公钥、证书签名和真实安装仍关闭；Windows 自动安装在恢复尚未验证时明确拒绝。此文件不代表真实系统更新验收。

## 启动与安装顺序

安装前持有维护 lease 和 helper 独占锁，确认没有活动任务或在途修改；签名与版本校验使用已下载的同一份字节。macOS 验证目标 bundle 标识、版本、arm64 和固定证书后，创建一致 SQLite 备份，并保存原/新应用树、原数据逻辑内容及备份字节 hash。

维护与准备都先检查配置 journal，未完成、冲突、未知阶段或缺少对应备份的已提交记录会阻止更新，不把配置恢复带进新版本启动。pending 的存在性使用不跟随链接的检查，畸形文件和悬空链接均阻断普通 Store 与 helper。

`updates/pending.json` 独立于 SQLite，采用有界、拒绝未知字段的格式。操作 UUID、安装注册标识、平台和版本绑定事务，应用与操作路径从已登记 root、当前 bundle 和 UUID 推导；不接受 journal 指定任意路径。`prepared` 在实际交换应用树之前持久化，随后启动根据两棵树的实际 hash 判断是否发生交换。

GUI 先取得进程锁，再进入恢复协调器，最后才打开普通 Store。验证阶段持 helper 独占锁，只在私有工作副本执行 schema、完整性和元数据校验，不调用 Vault、账户网络、客户端配置恢复或付费任务。确认数据库发布和 `committed` 持久化以后，才创建正常 Service 和部署 helper。

## 状态与中断

| 状态 | 恢复原则 |
| --- | --- |
| prepared | 未交换时保留旧应用并终止此次更新；已交换时先持久化 validating，不能盲目再交换 |
| validating | 仅在私有副本验证；上次进程没有提交成功时进入回退，不推断其成功 |
| rolling_back | 按持久化 claim 协调数据库及 WAL/SHM 的隔离和恢复，再恢复旧应用树 |
| committed | 允许正常启动，不能因后来正常数据变化再次回退旧快照 |
| rolled_back | 启动旧应用；已经映射新版二进制的进程停止，不继续打开数据库 |
| aborted | 实际未交换，保留原应用和数据 |

外部应用树、备份或无法证明由本事务写入的数据库家族发生变化时停止覆盖并报告冲突。数据库检查通过有界私有 family 副本读取，比较复制前后原文件 claim；不会为只读检查在原目录创建 WAL/SHM，也不使用忽略 WAL 的 immutable 模式。多文件和应用交换仍是可恢复协调，不是全局原子事务；hash 检查不能排除不遵守锁的外部写入竞争。

回退副本在发布前清除活跃连接、账户缓存、客户端载入/连接证据，禁用 helper 绑定和会话，提高授权 epoch，保留不含秘密的清理引用。Vault 的值不进入快照，不覆盖、不恢复，也不重新授予旧凭据。helper 在打开只读 Store 前及返回 token 前检查 pending，未完成或畸形事务会拒绝交付。

下一次更新可受控退役前一事务的终态材料：先核对当前应用、备份、隔离文件和允许的操作目录内容，持久化剩余树的逐项 seal，再逐项删除并同步目录。中断后仅删除仍与 seal 相符的剩余内容；改变或新增的材料会阻止继续删除，安装注册标识保留。正常启动不会因终态 journal 再次覆盖后来产生的数据。

## 证据与未完成项

`runtime/logs/native-update-recovery-fault-tests.log` 保留首轮失败：SQLite 只读检查意外生成原目录的 sidecars。修改为受控副本后，`native-update-recovery-fault-tests-2.log` 的7组通过；后续审查补充了终态退役中断、外来材料、未完成配置、悬空标记，以及已认领并发布的 live S2 数据库在普通 Store 打开前恢复 S1 的夹具。未认领的外来 S2 数据库保持原样并报告冲突。完整回归、失败原因、源码绑定和候选记录以[验证记录](validation.md)及最终阶段证据为准，不将中间通过的日志当成最终源码证据。

这些文件夹具验证项目内的协调逻辑，不能证明真实连续升级。真实 macOS 安装、启动、签名、Vault 连续性及回退，macOS 15 最低系统和 Windows 恢复仍需专用环境与授权。两个真实 Desktop 的配置载入、managed policy、模型和工具联调属于另行明确记录的未完成工作。
